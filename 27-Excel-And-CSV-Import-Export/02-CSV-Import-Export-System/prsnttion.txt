
# ERD PRESENTATION (Natural Flow - Urdu)

**Assalam-o-Alaikum Sir/Ma'am.**

Mera naam Aqsa Riyasat hai aur aaj main apne project **Online Blogging Application** ki **Entity Relationship Diagram (ERD)** present karungi.

Sab se pehle agar hum kisi bhi software ko develop karna chahte hain to uski coding se pehle hume uska database design karna padta hai. Agar hum bina planning ke database bana dein to future mein duplicate data, incorrect relationships aur maintenance issues aa sakte hain. Isi problem ko solve karne ke liye hum **Entity Relationship Diagram**, yani **ERD**, design karte hain.

ERD asal mein database ka blueprint hota hai. Ismein hum decide karte hain ke system mein kaunsi information store hogi, woh information kis table mein hogi aur different tables ek doosre ke saath kis tarah connected hongi.

Maine bhi apne project ki coding shuru karne se pehle sab se pehle uski **SRS** ko study kiya. SRS ko analyze karne ke baad maine system ki requirements ko identify kiya aur dekha ke mere project mein do main actors hain: **Admin** aur **User**. In dono ki functionalities ko dekhte hue maine un tamam data objects ko identify kiya jinhen permanently database mein store karna zaroori tha.

Database design mein inhi data objects ko **Entities** kaha jata hai.

Isi liye mere project mein total **7 entities** hain:

**User, Category, Post, Comment, Feedback, Follow aur Blog Setting.**

Har entity ek alag table represent karti hai.

Ab agar hum **User** entity ki baat karein to ismein registered users ki information store hoti hai. Lekin sirf entity banana kaafi nahi hota. Har entity ke baare mein kuch information bhi store karni hoti hai aur us information ko hum **Attributes** kehte hain.

For example, User entity ke attributes hain **user_id, first_name, last_name, email, password, gender, role aur status.**

Isi tarah **Post** entity ke attributes hain **title, content, image, post_date aur allow_discussion.**

Yani har entity ke attributes us entity ki properties ko describe karte hain.

Ab ek aur important question ye hota hai ke agar User table mein hazaron users hon to database ko kaise pata chalega ke kaunsa record kis user ka hai?

Isi problem ko solve karne ke liye hum **Primary Key** use karte hain.

Mere project mein User table ki Primary Key **user_id** hai, Post table ki **post_id** hai aur Category table ki **category_id** hai. Primary Key har record ko uniquely identify karti hai aur duplicate ya NULL nahi ho sakti.

Ab tak humne alag alag tables bana li hain, lekin agar ye tables ek doosre se connected hi na hon to database ka koi faida nahi hoga.

Isi liye hum **Foreign Key** use karte hain.

For example, meri **Post** table mein **user_id** Foreign Key hai jo User table ke **user_id** ko reference karti hai. Is se hume pata chalta hai ke ye post kis user ne create ki hai.

Isi tarah **category_id**, Post ko Category table ke saath connect karti hai aur Comment table ka **post_id** aur **user_id**, comments ko respective post aur user ke saath link karte hain.

Jab hum Foreign Keys ke through tables ko connect karte hain to un connections ko **Relationships** kaha jata hai.

Mere project mein ek User bohot sari Posts create kar sakta hai, ek Category ke andar bohot sari Posts ho sakti hain aur ek Post par bohot sare Comments aa sakte hain.

Ye sirf relationships nahi hain, balke ye hume ek aur concept ki taraf le jati hain jise **Cardinality** kehte hain.

Cardinality batati hai ke ek entity ka ek record doosri entity ke kitne records ke saath relate ho sakta hai.

Mere project mein sab se zyada **One-to-Many** cardinality use hui hai.

Jaise:

Ek User → Multiple Posts

Ek Category → Multiple Posts

Ek Post → Multiple Comments

Ye relationships real-world blogging system ko exactly represent karti hain.

Ab jab hum database design karte hain to sirf tables banana hi kaafi nahi hota. Hume ye bhi dekhna hota hai ke kahin unnecessary duplicate data to store nahi ho raha.

Isi liye hum **Normalization** apply karte hain.

Normalization ka basic purpose redundancy ko reduce karna aur database ko efficient banana hota hai.

For example, agar main har Post ke andar Category Name store karti to "Technology" category har post mein baar baar repeat hoti.

Is repetition ko avoid karne ke liye maine Category ki alag table banayi aur Post table mein sirf **category_id** store ki.

Isi tarah maine User, Post, Comment, Feedback, Follow aur Blog Setting ke liye bhi separate tables banayi hain. Is design ki wajah se database maintain karna easy ho jata hai aur future mein agar kisi category ka naam change karna ho to sirf ek hi table update karni padti hai.

Saath hi maine **constraints** bhi use ki hain, jaise **Primary Key, Foreign Key, NOT NULL, UNIQUE aur ENUM**, taake database mein sirf valid aur consistent data hi store ho.

Aakhir mein, meri ERD mein total **7 entities** hain jo Primary Keys aur Foreign Keys ke through connected hain. Ye design meri SRS ki tamam functional requirements ko fulfill karta hai, redundancy ko reduce karta hai, referential integrity maintain karta hai aur ek scalable database provide karta hai.
